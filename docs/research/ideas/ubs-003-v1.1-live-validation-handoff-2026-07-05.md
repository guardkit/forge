## 4. The loop, end to end (summary — full version in the jarvis GB10 handoff §2)

```
forge gate → ApprovalRequestPayload on agents.approval.forge.{build_id} (AGENTS)
           → BuildPausedPayload on pipeline.build-paused.{feature_id} (PIPELINE)
jarvis captures request_id/correlation_id/subject (TTL map, keyed by build_id)
jarvis SlackNotifier → pause message w/ Block Kit Approve/Reject buttons
operator taps → jarvis Socket Mode reply client:
   ack first → gate on payload.user.id == JARVIS_SLACK_OPERATOR_USER_ID
   → first-click-wins (handler lock)
   → ApprovalResponsePayload(request_id, decision, decided_by) on {approval_subject}.response
forge ApprovalSubscriber.await_response — 4-step chain:
   payload valid → decided_by == expected_approver → correlation_id match → request_id 300s dedup
   approve → mark_resume_pending → build-resumed…terminal
   reject  → CANCELLED in SQLite → build-cancelled (JNB-102)
```
Contracts pinned by tests (don't change casually): button value JSON
`{request_id,build_id,correlation_id,approval_subject}` < 2000 chars, action_ids
`forge_approve`/`forge_reject`; `build_id` is the 4th subject token; all
approval traffic on the AGENTS stream (overlap legal); PIPELINE keeps exactly
ONE ephemeral jarvis consumer (any `err_code 10100` = hard fail); everything
in-memory (DDR-027); nothing raises into a JS callback/socket/supervisor (DDR-007).

**Design note (why the two forge builds differed):** origin/main's FEAT-1872
emits build-cancelled for the CLI-cancel path via a dedicated `cli_runtime`
cancelled-notifier — NOT by threading a `pipeline_publisher` through
`CliSteeringHandler` (that was the discarded local build's approach). Trust the
committed `ff2489c` design.
