## 3. Build-babysitting playbook (hard-won on FEAT-28FF)

- **Division of labour**: the Player↔Coach loop converges task-scoped
  failures fine — DON'T intervene there. Intervene only at task-failure
  boundaries for cross-task composition breaks the Player can't see (stale
  shared constants, pacing-vs-timing interactions, test pollution). Fix in
  the worktree, run the FULL suite, commit `[guardkit-checkpoint] ...`,
  resume.
- **Resume semantics**: `--resume` fast-forwards approved waves (approvals
  preserved) and re-runs the failed task. `--refresh` rebases onto
  **origin/main** and conflicts with player commits — avoid; use `--fresh`
  from local main only for full restarts.
- **Verify green YOURSELF via JUnit XML** — `-q` prints no summary line in
  these repos (warnings quirk), and there are known false-green classes:
  `pytest --junitxml=/tmp/x.xml` then parse. Always
  `./.venv/bin/python -m pytest` (repo venvs; bare `pytest` = system 3.14
  = instant collection failure).
- **Known test traps** (all bit us; all in memory
  `guardkit-harness-default-langgraph.md`): structlog
  `capture_logs()` is order-fragile under `cache_logger_on_first_use` —
  assert drops/dedup BEHAVIOURALLY (repo convention, operator-confirmed);
  never patch `module.time.monotonic` (freezes asyncio's clock → suite
  hangs) — jarvis has an injectable `slack_notifier._monotonic` seam;
  fixed sleeps vs the notifier's ~1 msg/s pacing — poll with deadline.
- **Coach feedback blind spots**: runtime-parity failures don't name the
  failing test — if a task burns 2+ turns on parity, run the suite yourself
  and diagnose (test pollution shows as passes-alone-fails-in-suite).
- **Smoke gates**: both YAMLs already carry venv-explicit commands
  (`./.venv/bin/python -m pytest tests -x -q`). If a gate blocks the wave
  that would fix its own failure (chicken-and-egg), move the gate's
  `after_wave`, don't fight it.
